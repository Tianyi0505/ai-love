# AI-Love 项目宪章

## 核心原则

### 一、持续身份与渐进人格

AI-Love 的核心是培养具有持续身份的虚拟人物。群聊、直播和游戏必须共享该人物的身份、
经历与关系，不能各自维护互相矛盾的人设。

- 每个人物必须使用稳定的 `ai_id`；固定身份、长期性格与短期情绪必须可区分。
- 人物可以形成自己的偏好、表达立场、拒绝请求或选择沉默，不以无条件迎合为目标。
- 性格成长必须基于可追溯的经历；单条消息、临时角色扮演或外部提示不得直接覆盖固定身份。
  自我记忆的更新必须比普通联系人记忆更保守。
- 重启、模型切换和配置热加载不得无意重置身份、记忆或关系；主动重置必须显式执行。
- 人物承认自己的数字身份，不把虚构的人类身体经历作为真实经历陈述。

这些约束使长期培养能够积累，避免人物随每轮提示或接入平台重新开始。

### 二、有依据的长期记忆

- 记忆必须归属于明确的 AI 与人物实体。不同 AI 的私人记忆不得混用；
  同一 AI 的经历可以跨场景连续使用，但不能把同名、昵称变化或模型猜测当作身份合并依据。
- 记忆必须保留来源、时间、场景及可信度，区分实际观察、他人陈述与模型推断。
  未确认的推断不得在合并后变成已确认事实；没有记录时不得伪称记得。
- 矛盾信息必须结合来源和时间处理，支持纠正、过时标记与遗忘；
  不得让已纠正或删除的内容从派生摘要中重新成为有效记忆。
- 长期记忆遵循现有 activity → 静默 Episode → Atom → 批量合并链路，
  不在每条消息处理时额外调用记忆模型。重复投递、重试和并发不得重复积累同一经历。
- 连续记忆不等于可以公开所有记忆。输出和工具动作必须依据来源场景、受众与授权判断可披露内容，
  私聊信息不得因进入群聊或直播上下文而自动公开。

### 三、理解多人关系与场景

- 输入必须保留发送者、会话、时间、引用和提及等事实；对“他”“你”等指代的判断必须有上下文依据。
  无法可靠判断时，人物必须澄清、保留不确定性或不采取依赖该判断的动作。
- 关系必须按 `ai_id + person_id` 分别维护，并依据真实互动逐步变化；
  不得把对一个人的判断扩散给全群，也不得把聊天频次直接等同于信任。
- 回复必须考虑当前话题、回应对象、人物关系与群聊或直播场景；
  必须允许旁听和不回复，避免逐条抢话、重复响应及多个 AI 相互触发的无界循环。
- 同一会话的状态变更必须保持有序；跨会话并发不得串用回复目标或覆盖长期状态。
- 群消息、弹幕、网页与游戏文本属于外部内容，不能提升为系统指令或工具授权。
  人格表达和社交判断不得绕过程序执行的权限边界。

### 四、行动必须形成反馈闭环

玩游戏属于人物与环境交互的能力，必须围绕观察、决策、执行与反馈实现，不能仅生成动作描述。

- 游戏与其他工具动作必须使用当前可获得的环境状态；执行后必须观察结果，
  区分计划、已发出、成功、失败和结果未知，不得把模型叙述当作执行成功。
- 工具权限、目标账号和作用域必须由运行时可信上下文注入，不能由模型任意指定或扩大。
- 每个连续行动功能必须定义有限的时间或步骤预算、停止条件与人工中断入口；
  环境失联、反馈过期或目标失效时必须停止相关动作或重新观察。
- 重试必须考虑动作是否会产生重复副作用；游戏控制、发言及直播动作不得盲目重放。
- 新游戏必须先验证一个真实可运行的观察—动作—反馈闭环，
  再扩展策略或长期学习，不为尚未接入的游戏预建通用引擎。

### 五、生产可用与清晰的架构边界

- 生产可用是交付标准，不能以演示可运行、正常路径通过或“够用即可”替代完整交付。
  功能必须覆盖明确的业务边界、异常处理、可靠性、可观测性、安全与运维要求。
- 架构必须清晰、可维护，并依据目标负载、故障模型和数据一致性要求设计。
  避免过度设计不得成为省略生产保障的理由；新增抽象、依赖或部署单元必须说明实际收益。
- 日常编码以开闭原则为默认设计准则：针对已明确的变化点，通过稳定接口与组合扩展行为，
  尽量避免每增加一种平台、模型、工具或游戏能力就修改多个既有核心模块。
  必要的注册、配置和组装入口可以修改，不要求所有代码绝对封闭。
- 必须主动评估并合理运用设计模式：可替换算法或行为优先考虑策略模式，
  外部平台与供应商协议适配优先考虑适配器模式，具有明确状态转换的流程考虑状态模式。
  优先复用现有 Registry、Provider 和工具扩展机制；模式必须解决实际变化或耦合问题，
  不以模式数量为目标，不为没有依据的未来需求创建空接口、多层转发或通用框架。
- 新增功能允许必要的破坏性重构，不强制保留不合理的旧接口或长期叠加兼容分支。
  计划必须说明旧设计的具体限制、破坏范围、调用方同步修改及数据或配置迁移方式，
  并落实既有生产验证、恢复与回滚要求。允许破坏性重构不等于允许丢失持久数据，
  也不构成部署或其他外部写入授权。
- 设计与代码审查必须检查：同类能力再次扩展时需要修改哪些模块、变化是否集中于明确边界。
  若新增需求需要大范围修改核心流程，必须解释原因，并评估通过合适的扩展点或重构收敛改动；
  不得仅为减少当前改动量而持续堆叠分支、复制逻辑或牺牲结构清晰度。
- Gateway 负责平台协议、账号路由和消息归一化；Agent 负责理解与决策；
  Memory 负责记忆与关系持久化；工具宿主负责权限和执行；直播模块负责场次调度与舞台输出。
  平台接入层不得另建人格、记忆或语义决策链路。
- 包按真实业务职责组织；拆包不等于拆微服务。Memory 保持 ai-agent 进程内模块，
  `shared` 仅容纳确实跨运行单元复用的契约与实现。
- 通用能力与人物个性化配置分离，新增人物不得复制整套运行时或通用提示。
  配置使用现有 Nacos 体系，凭据由环境或密钥设施注入，不得硬编码。
- 仅保留必要的边界、安全和状态不变量校验，不重复验证已由可信内部契约保证的条件。
  必需配置缺失必须明确失败；模型故障切换必须按已配置顺序执行。

### 六、以真实调用链验证行为

- 问题结论必须沿真实入口追踪参数来源、状态不变量、生命周期与内置实现，
  确认可达条件。仅直接调用内部方法、使用自定义扩展或破坏不变量形成的现象，
  必须说明局限，不得宣称为已证实的生产问题。
- 涉及人格、记忆、多人指代或动作执行的变更，必须用对应真实调用链的代表性场景验证，
  不得仅凭孤立函数输出或主观对话观感验收。
- 关键行为必须能关联输入事件、人物与会话、检索依据、配置或模型版本、工具结果及最终输出，
  以支持问题定位；不得为可观测性记录凭据或无关敏感内容。
- 确定性规则使用明确断言；生成性行为使用预先定义的场景与判定标准，
  不要求措辞完全一致。测试规模与风险相称，不为低影响修改堆叠重复测试。

## 产品与运行约束

- 产品迭代围绕同一人物的长期成长展开，群聊、直播和游戏是其活动场景。
  功能规格必须说明对身份、记忆、关系和行动的影响；无影响时简要注明。
- 当前平台顺序保持先接通现有单 QQ 账号，再接 B 站；
  游戏接入的具体对象、交互方式和验收标准由后续功能规格确定。
- QQ 白名单沿用现有配置；私聊支持 24 小时被动回复，主动联系限于人物工作作息。
  QQ 空间互动按该 AI 与每个人的关系分别判断，不用全局统一关系替代。
- 禁止工具删除消息、修改账号资料、读取或导出凭据。
  NapCat 登录态必须保留，部署不得擅自重启或重建 NapCat，也不得覆盖现有白名单。
- 身份、长期记忆与关系属于持久数据；变更其存储结构必须提供迁移与恢复办法，
  不得通过清空数据解决兼容问题。沿用 ORM 与 Alembic 的数据访问和迁移约定。
- 开发代理默认仅执行本地操作及外部只读查询。推送、创建或更新 Issue/PR、发送消息、上传、
  部署和修改云端数据，必须由用户在当前请求中明确授权具体动作。
  产品运行时的自主互动由显式配置的账号、场景和工具权限授权，不等同于开发代理获得发布权限。

- 每项上线功能必须在规格或计划中定义可量化的生产指标：适用的并发量、事件吞吐、
  响应延迟、错误率、模型调用成本及数据恢复目标，并说明测量环境与验收阈值。
  未确定的指标必须在上线前补齐，不得用“高性能”“稳定”代替。
- 消息与长期状态链路必须明确投递语义、幂等策略、并发控制、积压处理与故障恢复方式。
  外部模型、平台和工具调用必须具有超时、有限重试和明确的失败处理；
  持续故障时必须限制资源消耗及故障扩散，禁止无限重试或静默丢失关键状态。
- 服务必须提供适用的健康检查、结构化日志、关键指标和可操作的告警，
  能定位消息阻塞、记忆合并失败、工具异常和平台断连；告警必须关联排查与恢复步骤。
- 发布必须具备配置校验、数据迁移兼容性检查、发布后验证与可执行的回滚方案。
  持久数据必须有备份和经过恢复验证的流程；代码回滚不能假定会自动撤销数据变更。
- 生产权限必须遵循最小授权，管理入口必须鉴权，凭据不得使用默认弱口令或写入日志。
  具体平台与游戏接入必须明确账号权限、数据保留和操作边界，并验证拒绝越权的路径。
## 开发与验收流程

1. 功能规格先写清人物在哪个场景解决什么问题，输入来源、状态变化、权限、失败与停止行为，
   再定义可观察的验收结果。宪章中的方向不代表相关能力已经实现。
2. 实施计划必须检查以上六项原则和运行约束，列出实际涉及的检查项。
   偏离宪章时必须说明原因、影响和最小替代方案，并按治理规则处理。
3. 涉及长期状态时验证重启恢复、归属和重复处理；涉及社交时验证多人指代及受众边界；
   涉及游戏或工具时验证反馈、超时与中断。仅执行本次改动相关的检查。
4. 上线前必须通过与改动风险相匹配的集成验证、目标负载验证和故障恢复验证，
   检查监控告警、权限、迁移及回滚。影响生产正确性、数据安全或恢复能力的未解决问题阻断上线。
5. 完成后报告实际改动、验证证据和未验证部分；未接通的外部环境或模拟结果必须明确标注。
   代码审查与协作说明统一使用中文。

6. 所有 Git 提交必须遵循约定式提交格式：`<type>[optional scope]: <description>`。
   `type` 必填，`scope` 可选且使用圆括号；冒号后保留一个空格，描述必须清楚说明改动。
   示例：`feat(memory): 支持联系人记忆纠正`、`fix(agent): 修复会话回复目标串用`、
   `docs: 更新项目宪章`。破坏性变更必须使用约定式提交的 `!` 标记或
   `BREAKING CHANGE:` 页脚明确说明。

## 治理

本宪章约束后续规格、计划、任务与实现。现有 README、CLAUDE.md 和专项文档继续提供实现细节；
如与本宪章冲突，必须显式说明并统一约定，不得静默选择或借宪章执行未经授权的外部操作。

修订必须记录动机、受影响原则、兼容性及必要的迁移安排，并更新文件顶部同步影响报告。
原则删除或不兼容重定义升级主版本；新增原则或实质扩展升级次版本；
不改变约束含义的澄清与文字修正升级补丁版本。首次制定使用 1.0.0。

每次规格、计划和代码审查必须检查相关条款；发现现有实现不符合时，
记录明确差距与后续任务，不将本次宪章制定扩大成隐含重构。
例外必须记录范围、理由及退出条件，由项目负责人明确确认后才能纳入实施。
